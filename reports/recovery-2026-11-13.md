# WhatDateTime — 2026-11-13 date/time and discovery repair

## Scope and evidence

The current project is Astro with React islands, not Next.js. Existing tools, page families, styling and assets-first Cloudflare deployment are retained. Initial worktree was clean on `fix/project-review-20261105` at `740f483`. All operating files were read before implementation.

The owner supplied the August 11–November 10 GSC summary: 316 clicks, 253,726 impressions, 96.45% of impressions in August 12–16, and 65 impressions/zero clicks in the last 28 days. The original workbook and GSC reports are not available here. The linked private report requires authentication. These figures do not establish a penalty or the cause of the decline. Google's [traffic-drop investigation guide](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops) calls for comparing search/report evidence rather than assigning a cause from one symptom.

A public read of `/8-hours-from-now` still showed a September 26 answer with live wording. Local code confirms the origin: `lib/build-time.ts` deliberately defaults to `2026-09-26T04:00:00.000Z` to avoid changing thousands of assets on each build. Independent React timers and form state also allowed the answer, timeline and related results to diverge after a custom calculation. Neither observation proves the cause of search loss.

## Implementation

1. `lib/relative-state.ts` and `components/use-relative-state.ts` share one applied state across relative-answer islands: instant, IANA zone, amount, direction, unit and example/live/custom mode. Hours use elapsed time; dates use calendar arithmetic in the selected zone. First edit freezes the live starting point. Calculate applies the draft; reset resumes the device clock. Minute-boundary updates and focus/visibility recovery do not emit analytics events.
2. Initial HTML uses an explicitly labeled fixed UTC example. Build timezone is UTC, and an invalid reference environment variable fails fast. Browser detection replaces the example with device-local live output. The stable reference remains intentionally unchanged; no daily full-site upload, Worker-first routing or framework migration was introduced.
3. Direct answers, formulas, calendar highlights, timelines, nearby rows and hour-copy content share the applied calculation. The 24-hour table handles skipped and repeated local hours. Hour timelines use the actual midpoint (including half an hour). Date calculator input is protected from refresh and has a reset-to-today action.
4. `/calculations/hours-from-now` now includes the existing calculator above its directory and pagination. `/calculators/business-days` is a reusable tool, linked from the homepage/navigation and answer pages. Its rules exclude Saturday/Sunday and the start date, not public holidays. All existing numerical URLs remain accessible.
5. Countdown supports an event name, named timezone, explicit local save/restore, clear/reset and a share fragment containing the exact UTC target instant. New recipients keep the same instant and source zone, including when following a different share fragment on an already open countdown page. Invalid/ambiguous/nonexistent wall times are rejected, not silently guessed. No account/database was added. Explicit action analytics omit entered values; GA page location omits countdown fragments while retaining existing campaign parameters.
6. City-pair summaries, seasonal offsets, FAQs and conversion tables use the selected planner date. Live city clocks remain separately labeled. Method FAQs now cover the relevant hour, date or business-day rules and feed both visible FAQ and JSON-LD. Countdown instructions, methodology, About and privacy text reflect actual behavior.
7. `/35-business-days-from-today` was excluded by the old family threshold, not missing as a route. It is restored as one protected indexable page based on the owner's 2-click/155-impression history and maintained functionality. The existing 13 sitemap shards remain; stable revision dates advance for material changes, not clock ticks. No existing route is deleted or redirected, and no numeric page is added.

## Validation

Source gates run: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` and `npm run seo:check`. The build gate directly inspects 2,238 static HTML files and 20 on-demand HTML samples, checks all 10,263 metadata records, canonical/robots consistency, JSON-LD parsing, sitemap eligibility and crawlable paths. Maximum eligible crawl depth remains six. Module-type inference notices from Node are warnings, not test failures.

`npm run test:ssr` exercises 44 routes through the local Cloudflare runtime using real navigation headers, including all 14 requested samples, the new business-day tool, and the hour directory. It also tests query canonical consistency, HEAD, existing aliases and seven real 404s. Evidence: `reports/http-smoke.json`. Both canonical and www Workers passed `wrangler deploy --dry-run`; this performs packaging, not publishing.

Calculation regressions cover 23:30 + 2 elapsed hours = next-day 01:30, February 28, 2028 + 1 calendar day = February 29, both month-end addition/subtraction, weekend skipping and zero/start-day rules. Four host time zones and three reference dates exercise initial SSR hydration stability. Explicit New York fixtures distinguish a 23-hour calendar day from 24 elapsed hours and the repeated 01:30 hour. Existing timezone tests cover skipped/repeated hours, fractional offsets and all 82 named city zones. Countdown hash/storage roundtrips reject malformed targets.

Browser checks use the agent-browser skill against built Cloudflare assets. A custom 23:30 + 2 hours kept the answer, formula, midpoint timeline, related current row and copied text aligned at next-day 01:30. Simulating a later clock and focus refresh did not replace custom inputs. Reset resumed live mode. Friday + 1 business day matched Monday in both the calendar highlight and related table. Date-tool leap-day input survived a focus refresh. Selecting July 15, 2027 on Singapore → Melbourne changed the summary to 09:00 → 11:00 (2 hours), and did not get overwritten by live-clock refresh. Countdown saved/restored a Tokyo 09:30 target as `2028-02-29T00:30:00.000Z`, retained it after reload and fresh share navigation, and cleared saved storage. An already-open-page share-fragment issue found during QA was fixed and retested in the final pass.

Sampled 390px mobile layouts had no horizontal overflow, and the 1440px hour-directory screenshot retains its calculator and list. Screenshots are local ignored artifacts in `dogfood-output/recovery-*.png`; they are not a pixel-perfect comparison with the previous release. Browser errors were empty in the exercised flows. Captured analytics contained only explicit calculate/copy/save/share events, not automatic ticks or input values.

A local 390px hour-page measurement gave LCP 100 ms and CLS 0.02 (warm local runtime, no production network throttling; not CrUX or a Lighthouse score). Inspecting serialized props found unnecessary full editorial records in the live nearby-results island. Passing only calculation fields reduced the sampled business-day HTML from about 100 KB to about 54 KB before compression. No dependency was added. Production/GSC verification is not represented by these local tests.
